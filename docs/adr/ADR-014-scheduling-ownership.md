# ADR-014：调度配置进产品界面，但执行留在独立 worker

**状态：已采纳**
**日期：2026-09-19**
**依据：** 主规格 §14.2、补充 v0.2.1 §4 / v0.2.2 §1（调度所有权）、`docs/daily-pipeline.md`

## 背景

每日流水线（`tools/daily_run.py`）早就写完了：并发锁、休市判断、留痕、告警都在，
但**机器上没有任何调度在跑它**——留痕末日 2026-09-16，而数据停在 2026-09-14。
界面上不会出现任何异常，只有 `/api/v1/status` 的 freshness 会说它 stale。

原先的安排是"使用者自己去注册 Windows 任务计划程序或 cron"（`docs/daily-pipeline.md`）。
这个安排在纸面上成立，实际后果是：

* "每天几点跑"是一个使用者**每天都会关心**的产品设置，却被藏在运维里；
* 没注册这件事没有任何产品内提示，只有数据慢慢变旧；
* 一旦要改时间，改动发生在产品之外，产品里查不到"现在配的是什么"。

## 决策

**配置进产品，执行留在独立 worker。**

| 项 | 决定 | 理由 |
|---|---|---|
| 配置存放 | 产品库 `run_schedule` 单行表 | API 与 worker 共用同一份事实，不需要约定本机路径 |
| 配置入口 | 界面「设置」页 → `GET/POST /api/v1/schedule` | 改时间不必离开产品 |
| 执行者 | `tools/scheduler_worker.py`（长驻独立进程） | §14.2「独立 worker」；见下 |
| 「立刻运行」 | `POST /api/v1/schedule/run` **只登记请求** | 与到点触发共用一条通道，两条入口不会分叉 |
| 结果 | 留痕文件仍是权威；`pipeline_last_run` 只是摘要 | 界面上不应该去 grep 日志 |

### 为什么执行**不**放在 API 进程里

三个具体的坏结果，都不是理论担忧：

1. **API 一重启，当天那次就没了**，而且没有任何东西会告诉使用者；
2. 采集要跑几十秒到几分钟，跑在 API 进程里会与请求争用同一个 SQLite 连接；
3. 多个实例（或容器被重启成两份）会各自到点触发，变成两次并发采集写同一份缓存
   ——正是 `daily_run` 的锁要防的事。

### 与"系统调度"的关系

本 ADR **不取消**系统调度这条路：`tools/daily_run.py` 仍然可以直接挂到
Windows 任务计划程序或 cron 上，两种方式互斥也可以并存（锁与"每天至多一次"
的判据都是幂等的）。本 ADR 只是把那件事从**唯一途径**降级为**可选项**。

若将来要让系统调度负责"拉起 worker"（而不是直接跑流水线），
推荐的形式是"开机/登录时拉起 worker 长驻"，而不是"每天定点跑一次脚本"——
后者会让"到点没跑"重新变成一个没人看得见的失败。

## 后果

- 使用者可以在界面里改时间、启停、立刻运行，并看到**最近一次运行的每一步结果**；
- 代价：多了一个需要长驻的进程。**它不在跑时，界面上的配置不会让任何东西自动跑**——
  这一点必须写在设置页上（已写），否则会出现"我配了 20:30，但数据三天没动"
  而使用者以为已经配好了的情况；
- 默认**停用**，且启用时**必须填解释器**：装上就自动每天抓数据是使用者没做过的
  决定；而用错解释器（没装 baostock 的那个）每天都会失败，失败信息看起来却像
  数据源坏了；
- `schema/002_run_schedule.sql` 是新增表，不是修改 001——`apply_migrations()`
  靠 `IF NOT EXISTS` 幂等，**改已有表的列不会生效**（见 implementation-baseline §8.3）。
