## 1. 为什么需要这份文件

主文档与补充文档各有一套阶段划分，且存在三处实际矛盾：

| 矛盾 | 主文档 | 补充文档 | 本基线裁决 |
|---|---|---|---|
| 数据源决策的时点 | M0 是**第一道门**，M0 未完成不得进入 M1 | v0.2.2 §1 一处要求 Q1 前关闭数据源，§4 又把供应商决策排到第 5–7 周 | **拆成两件事**：真实数据验证从第 1 周并行启动；供应商**合同**可后置。见 §3 T3 |
| 是否依赖既有 AI 基座 | §0.1"独立轻量部署，不依赖已有企业平台底座"；`agentctl` 零命中 | v0.2.1"优先复用已有 agentctl" | 以主规格 §0.1 自身的例外条款衔接："不在未检查现有代码的情况下设计强耦合集成"。现已检查完毕，故接入成立，但**须新增 ADR 并修订 §14.3/§14.4**。见 §6 |
| Q3 的账本前置 | M2 才交付模拟与账本 | Q3 前置仅写"Q1 + 合成账户"，却要求验证"仅一次入账" | **Q3 依赖 M2**；且必须区分"确认冻结一次"与"模拟成交记账一次"。见 §3 T9 |

结论：**Q 系列依附于 M 系列，不是一个平行的第二条主线。** 接入是纵向能力，量化领域是横向底座。

## 5. 验收结论的三级口径（防止再次出现过度断言）

Q0 期间出现过一次"把测试接线错误当成产品缺陷"的误判（见 Q0 报告 §4.4）。为避免复发，本基线要求所有验收结论标注级别：

| 级别 | 含义 | 允许的措辞 |
|---|---|---|
| **L1 现象** | 只记录观察到的输入/输出 | "在 X 配置下观察到 Y" |
| **L2 行为** | 在**明确声明的配置**下，断言可复现 | "在配置 X 下，Y 被拒绝" |
| **L3 推断** | 由 L2 外推到未测配置 | **必须显式标注外推范围与未验证前提** |

规则：
1. 任何"系统缺陷"结论必须是 **L2**，且配置前提写在同一句里。
2. **测试接线本身是安全前提，必须被断言而非假定**——两个探针现在都要求产品令牌与 master 令牌分离。
3. 探针脚本**必须用退出码表达结论**，不能只是打印。收到响应 ≠ 通过。
4. 不修改基座即可解决问题时，不提出修改基座的建议。

### 8.3 事实修正：主规格**未**修订

§6 末段写着需要修订主文档 §14.3 / §14.4 / §16.3 / §20。**这件事没有做。**
截至 2026-09-16，`A-Quant-Lab_开发文档_v0.2.md` 里 `agentctl` 零命中，
ADR-011/012/013 也未被它引用。

诚实的表述是：ADR-011/012/013 是**仓库内**已采纳的决策，
而主规格仍是接入前的版本。二者尚未合并。

**这不阻塞开发**（代码与 ADR 一致），但它意味着"以主规格为准"这条规则
在这些议题上会指向一份过时的文档。

**同日更新：已用"定点修订"解决。** 新增 `docs/spec-revisions-2026-09.md`，
逐条声明哪一段被取代、取代它的是什么、依据在哪；主规格开头也加了指向它的警示。
冲突时以修订记录为准。

选择定点修订而不是就地改写主规格，理由是：主规格是**需求与验收的基准**，
被本基线、ADR 与实施文档多处引用。在 981 行里就地改动会让"主规格说了什么"
失去唯一性——而它是所有争议的最终裁决依据。定点修订保留了
"某年某月某日它是这么写的"这个事实。

修订过程中另外发现一条**实现限制**，已记入补遗 R2.1：
`apply_migrations()` 按序重放 `schema/*.sql`，靠 `IF NOT EXISTS` 幂等，
**没有版本表**。因此新增表会生效，而**已有表的列与约束变更不会生效**——
修改 schema 后必须显式重建数据目录。本项目已经踩过一次
（给 CHECK 白名单加取值、给表加列，都是靠重建快照才生效的）。

### 8.7 因子从来没有落过库，以及"配置写着却不生效"的第二例

**性质：** 本节记录的是两个**接线缺陷**，它们的形状与 §8.6 完全相同——
**每一段代码单独看都对，接起来是空的；而所有测试都是绿的。**

**缺陷一：因子算完只在内存里，从未进过产品。**

流水线的第三步写着"计算 F10 因子"，它跑的是
`tests.integration.t12_f10_real`——一个**验收脚本**：读采集缓存、在内存里算一遍、
写一份报告 JSON。于是两件事同时为真：

| 现象 | 事实 |
|---|---|
| 运行留痕 `计算 F10 因子 OK`；报告 `computed: 832/900, PASS` | 快照库里 `research_run` / `feature_value` **0 行** |
| 研究卡接口 200、结构完整 | 卡片上永远没有数值 |

研究卡读的是 `research_run` / `feature_value`（`snapshot_card_reader.py` 的
`_factors`），而落库路径（`compute_f10_for_snapshot`）只被"研究作业"接口
调用过。两条路径都在，谁也没接上谁。

配套还缺一环：**快照里根本没有财务数据集**，所以即使去落库，也只会得到
900 行「快照未包含财务数据」。现在 `t10_universe_snapshot.py` 把
`financials-cache.json` 按研究池过滤后随快照冻结。

**顺带的第二个洞**：研究卡接口调 `build_research_card` 时**没有传**
`factor_values`（它有默认值 `None`）。即便库里满是有值的行，卡片仍然是空的。
"参数有默认值"正是这类缺陷长期不报错的原因，因此新增了一条对着**真实调用点**
的守卫（`tests/api/test_research_card_factors.py`）。

**缺陷二：`exclude_listing_days` 声明了，但没有任何一行代码读它。**

`ConstructionParams.exclude_listing_days = 120` 一直在配置里，全仓库却只有两处
提到它：定义处，和一句"门槛由组合构建层按交易日计算"的注释。而组合构建层
**没有实现它**。这解释了 §8.6 那条注释为什么像是"已经处理过了"：参数存在，
注释写着在别处判，两件事都不成立，但看起来像已经完成。

现已实现在 `PlanService._filter_by_listing_age`，并说清它**能判什么、不能判什么**：

| 情形 | 判定 | 依据 |
|---|---|---|
| 上市日晚于决策日 | 排除（`NOT_LISTED_YET`） | 那时它还不是可交易证券 |
| 上市日在快照交易日历范围**之内** | 实际交易日数 < 门槛则排除（`LISTED_TOO_RECENTLY`） | 独立长日历精确计数 |
| 上市日在交易日历起点**之前** | 日历已覆盖门槛天数则判定达标；否则不排除并写 note | 单调证明，且短日历不猜测 |

采集器现把上证指数请求中约 800 个自然日范围内的权威交易日单独保存，快照发布器
按快照末日裁剪并要求至少 120 个交易日；逐只行情仍保留因子所需的短窗口。旧快照
没有长日历时继续 fail-safe：不误排除，并在 note 中披露覆盖不足。

**数据侧仍未关闭的部分**：`listed_on` 现在有数据了（BaoStock `ipoDate`，
900/900），但**研究池每次重建都会重写 `configs/real-pool-csrc.yaml`**——
`build_pool_from_universe.py` 原先不回落 `listed_on`，于是
`collect_listing_dates.py --write` 写进去的值会在下一次重建池子时消失，
门槛静默退回"不判"。现已改为从上市日期缓存回填（并打印"其中带上市日期 N 只"）。

**同一形状的第三例（验收脚本配置成生产不会用的样子）**：

### 8.6 Q1 handler 接 M1 存储：接完才发现的两个问题

这一段记录的是**接线过程中暴露出来的缺陷**，不是接线本身的做法。
两个缺陷有同一个形状：**一段从未被执行过的代码，被测试全绿地保存了下来。**

**缺陷一：能力被"注册成功"，却在第一次真实调用时失败。**

handler 从"读模块内写死的夹具"改成"读注入的读取器"时，`reader` 被写成
**必填关键字参数**。我自己的测试全部显式传了 `reader`，所以全绿；
而基座装载 handler 用的是：

```python
inspect.signature(function).bind({})   # 一个位置参数
```

于是接入侧会看到"handler 可装载"，直到真实调用才 `TypeError`。
`tests/security/test_agentctl_handler_contract.py` 现在把**基座真实的装载方式**
搬进测试：按 agentctl 的 sys.path 约定 import，再按它的规则校验签名。
该守卫已用修复前的签名实测会失败（`missing a required keyword-only argument`）。
同理，`capabilities/agentctl.capabilities.yaml` 的 `smoke:` 仍指着已被删除的
合成夹具 `SYN.A.600519 / snap-syn-001`，已改为真实快照 `SH.600519 / snap-universe`。

**缺陷二：`listed_on` 一旦有值，就会把证券判为不可模拟。**

`Instrument.is_simulatable` 里写着：

```python
if self.listed_on is not None:
    return False   # 上市天数门槛由组合构建层按交易日计算
```

注释说的是"门槛在别处算"，代码做的是"知道上市日期就排除"——
把一条**信息**当成了**排除条件**。它长期不可见，因为免费源没有采集上市日期，
`listed_on` 恒为 NULL，那段分支从未执行；而所有既有测试用的都是 `listed_on=None`
的标的，所以即使补上数据源、整池被清空，测试也仍然全绿。

现已按 §3.1 的措辞重写：只排除**决策时点尚未上市**与**已退市**两种情形；
上市天数门槛（`exclude_listing_days=120`，按**交易日**）留在组合构建层——
本方法拿不到交易日历，在这里用自然日近似会静默地多留下新股。
守卫见 `tests/pit/test_simulatable_listing_window.py`，同样已实测对旧谓词失败。

**副产品（已关闭）**：`listed_on` 原先没有任何数据源在写。现已用 BaoStock 的
`ipoDate` 逐只补齐（`tools/collect_listing_dates.py`，900/900 命中），并由
`build_pool_from_universe.py` 回填进研究池、`t10_universe_snapshot.py` 带进快照。
在此之前，能力卡片会如实说"缺少上市日期：无法判断历史时点是否已上市"——
那句限制当时是真的，不是占位文案。
