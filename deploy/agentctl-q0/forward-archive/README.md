# 前向归档（forward archive）

这个目录回答一个问题：

> 你说某条消息"在那个时点已经可得"，凭什么？

不是靠回忆，也不是靠数据商的一句"我们做了 point-in-time 处理"，而是靠
**当时真的抓下来了什么、什么时刻抓的、字节的哈希是多少**。归档是项目里
唯一能把 PIT 声明钉死的东西，所以它的证据链必须自己站得住。

## 目录结构

| 路径 | 是什么 | 进版本库吗 |
| --- | --- | --- |
| `meta.sqlite` | 归档库索引：`raw_artifact`（内容寻址存储）与 `receipt`（每次抓取的收据） | 否（可由运行重建） |
| `raw/<前2位>/<完整64位哈希>` | 内容寻址的真实字节。任何抓取到的响应原文都按 sha256 落在这里，同一份内容只存一次 | 大体积者否，见下 |
| `t5-cninfo-run.json` | 最近一次 T5 运行的证据摘要：每条公告的 URL、`content_hash`、`byte_size`、`available_at`、`available_basis` | 是 |
| `t43-run-summary.json` / `t44-chain-summary.json` | 早期数据源链路探针的结论 | 是 |

内容寻址的布局由 `ForwardArchive.store_bytes` 决定，写死了
`rel = f"{hex[:2]}/{hex}"`——**目录取哈希前两位，文件名是完整 64 位哈希**。
不要凭直觉写成"目录两位 + 剩余部分"，那种路径会找不到任何文件。

## 关于大体积原始字节

单次 T5 运行即可产生 20 MiB 以上（年报、募集说明书常有上百页，
本目录里最大的一份是 19.7 MB 的募集说明书）。这些字节**留在磁盘上，
但不提交**，理由写在 `.gitignore` 里，此处重述要点：

1. **可验证性没有损失。** 摘要里记着每份文档的 URL 与 sha256，
   重新拉取一次就能逐字节复核——哈希对照表本身就是证据。
2. **版权未确认。** 巨潮公告的权利归属仍记为 `UNKNOWN`（见 README
   的数据能力卡），把权利未确认的第三方全文写进版本历史并不合适，
   而且 git 历史里的字节抹不干净。
3. **仓库不该线性膨胀。** 每跑一次多 20 MiB，历史很快就不可用。

因此 `raw/*/` 整体忽略，只保留体积小、可读、作为"探针回执"的 JSON
（用 `!raw/*/*.json` 重新纳入）。**本次运行的四份 JSON 回执仍然提交**，
它们是"我们确实收到过这些响应"的可离线复核的直接证据。

## 怎么复核

关闭网络也能跑，不依赖 pytest，不读环境变量：

```bash
python tools/verify_archive.py
```

它逐条检查四件事：

1. **内容寻址**——文件是否位于 `raw/<hash前2位>/<完整hash>`；
2. **体积一致**——磁盘字节数是否等于摘要里的 `document_bytes`；
3. **摘要一致**——重新计算的 sha256 是否等于 `document_content_hash`；
4. **头部一致**——PDF 记录是否真的以 `%PDF-` 开头。

退出码 0 表示全部通过；1 表示存在不一致（会逐条打印差异）；
2 表示还没有摘要（首次运行前的正常状态，不算失败）。

复核器本身也有测试：`tests/integration/test_archive_verification.py`
用合成归档逐项制造破坏——改一个字节、删掉字节、让摘要谎报体积、
把 HTML 冒充 PDF——要求复核器**必须**报错。一个只会说"通过"的复核器
比没有复核器更糟，它会把未验证的东西包装成已验证的结论。

> 复核器的路径算术也曾经写错（少识破了写入方的布局），结果把一次
> 完全正常的归档整批报成"字节不一致"。写那条 bug 的教训已经固化到
> `_cas_path` 的文档字符串里：**复核器的路径规则必须与写入方逐字一致**，
> 否则它的结论毫无意义。

## 怎么重跑 T5

只做只读抓取，**不下单、不连券商**。需要放行本机透明代理网段
（见 `docs/adr/ADR-002`）：

```powershell
cd E:\IT\A股量化交易
$env:PYTHONPATH='E:\IT\A股量化交易\src'
$env:AQUANT_TRUSTED_PROXY_NETWORKS='198.18.0.0/15,fdfe:dcba:9876::/48'
python -m tests.integration.t5_cninfo_archive_run
```

必须以模块方式（`-m`）从仓库根目录运行，否则 `import tests` 会失败。

| 环境变量 | 含义 | 默认 |
| --- | --- | --- |
| `T5_LOOKBACK_DAYS` | 公告窗口相对今天回看的天数 | 40 |
| `T5_COLUMN` | `szse`（深市）或 `sse`（沪市） | szse |
| `T5_LIMIT` | 取样公告条数 | 5 |
| `AQUANT_TRUSTED_PROXY_NETWORKS` | 允许的透明代理网段 | 空（不允许） |

成功判据不是"脚本退出 0"，而是三件事同时成立：
**列表抓取成功 + 每份 PDF 都归档成功 + 每份归档的哈希都复核通过**。

## 最近一次运行（2026-09-14）

- 日历源：`tencent-ifzq`，`sh000001`，267 个交易日（2025-08-11 ~ 2026-09-14）
- 公告：抓取 10 条，其中 5 条进入 PIT 就绪记录
- `available_at = 2026-08-12T00:45:00+00:00`，
  `available_basis = RECONSTRUCTED`，`pit_mode = HISTORICAL_RECONSTRUCTED`
- PDF 归档 5/5，哈希复核 5/5
- 归档收据：`cninfo` 19 条，去重后 13 份不同内容

最后一行值得单独说明：**13 份不同内容对应 5 条记录**，因为同一次运行里
列表查询被重试过（收据记录每次抓取），而内容寻址让重复响应只占一份空间。
所以"收据数"和"内容数"本来就不该相等，对不上不代表出错。

## 这批证据的边界

`available_basis = RECONSTRUCTED` 的含义是：**抓取发生在可用时点之后**，
可得时间是从公告日期反推出来的，不是当时观察到的。因此：

- 它可以用来证明"这条公告在那个日期已经存在"；
- 它**不能**用来做正式的点对点回测，因为
  `first_seen_at`（2026-09-14）晚于 `available_at`（2026-08-12）。

要拿到真正的 `LIVE_OBSERVED` 证据，只能靠定时前向抓取一天天积累。
摘要里每条记录的 `pit_mode_note` 都写明了这一点，请勿在引用时省略。
